# Рассылка в чат группы

Аргументы: `$ARGUMENTS`: тема сообщения своими словами (например «что нового в 1.22» или «ответ другу @Quatr_cmmn»), либо `photos 01-schedule.png,02-subgroups.png` для альбома скриншотов, либо `test` для пробного сообщения.

Сообщение уходит всей группе от имени бота и обратно не забирается. Поэтому **ничего не отправляй, пока пользователь не увидел точный текст (и список скриншотов) и не ответил «да»**. Разрешение на одно сообщение не распространяется на следующие.

## Как это устроено

- Рассылку делает GitHub Actions: `.github/workflows/telegram-release.yml`, репозиторий `ar1stov/pary-gstu`. Секреты `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` лежат в GitHub, токен нигде не выводи и не записывай.
- Ручной запуск (`workflow_dispatch`) берёт файлы **из репозитория на GitHub**, поэтому новый файл сообщения сначала нужно закоммитить и отправить (`git push`), иначе workflow его не найдёт.
- Сообщение о новой версии уходит само при публикации релиза (см. `/release`), отдельно его отправлять не нужно.

## Три режима

**1. Готовое сообщение (HTML).** Файл `.github/announcements/<имя>.html`. Имя только из латинских букв, цифр, точки, дефиса и подчёркивания, без точки в начале.
Оформление как в `launch.html`: заголовок `<b>…</b>`, абзацы через пустую строку, несколько эмодзи для структуры, ссылки `<a href="…">текст</a>`. Допустимы теги `b`, `i`, `u`, `s`, `a`, `code`, `pre`, `blockquote`. Символы `<`, `>` и `&` в обычном тексте пиши как `&lt;`, `&gt;`, `&amp;`, иначе Telegram отклонит сообщение. Длина не больше 4096 символов.
Контакт для багов: `@qwertyarstv`. Если нужно упомянуть человека из группы, пиши его ник как есть (например `@Quatr_cmmn`).
Запуск:
```bash
gh workflow run telegram-release.yml --repo ar1stov/pary-gstu -f message_file=<имя>.html
```

**2. Альбом скриншотов.** Файлы из `docs/screenshots/`, от 2 до 10 штук, подпись `caption` необязательна.
```bash
gh workflow run telegram-release.yml --repo ar1stov/pary-gstu -f photos=01-schedule.png,02-subgroups.png -f caption="Подпись"
```

**3. Пробное сообщение.** Короткий текст без разметки, для проверки бота:
```bash
gh workflow run telegram-release.yml --repo ar1stov/pary-gstu -f text="Пробное сообщение"
```

## Шаги

1. Определи режим по аргументам. Если неясно, спроси.
2. Напиши текст (режим 1) на русском, в живом студенческом тоне, без канцелярита. Для режима 1 сохрани его в `.github/announcements/<имя>.html`; имя придумай по смыслу (`update-1-22.html`), существующие файлы не перезаписывай без спроса.
3. **Покажи пользователю итоговый текст целиком** (или список скриншотов и подпись) и спроси, отправлять ли. Правки вноси и показывай заново.
4. Откажись отправлять и скажи об этом прямо, если текст оскорбляет конкретных людей, содержит чужие личные данные, ссылки или файлы не из проекта, либо выдаёт себя за сообщение от других людей. Шутки внутри группы, о которых все знают, допустимы, но в таких случаях предложи смягчить формулировки.
5. После «да» для режима 1: `git add` только файла сообщения, коммит в стиле проекта (`Рассылка: <тема>`), `git push origin main`. Для режимов 2 и 3 коммит не нужен.
6. Запусти workflow командой из нужного режима.
7. Подожди результат: `gh run list --repo ar1stov/pary-gstu --workflow telegram-release.yml --limit 1`, затем при необходимости `gh run view <id> --log-failed`. Не опрашивай в цикле: два-три запроса с паузой.
8. Скажи пользователю: ушло ли сообщение (workflow `success`), и попроси подтвердить по чату, что оно действительно пришло и выглядит нормально. Ошибка «can't parse entities» значит неверная HTML-разметка в тексте: исправь файл и предложи отправить заново, ничего не меняя в workflow.
